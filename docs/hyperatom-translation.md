# Семантическая трансляция гиператомов и Graphviz

## Что установлено по старому коду

Старый набор скриптов реализовывал конвейер из четырёх частей:

1. `atoms.py` сканировал файлы в дереве данных и передавал текст в отдельную Lark-грамматику для прежнего формата.
2. `ether_object_parser_transformer.py`, `ether_object.py`, `hyperobject.py` и `hyperatom.py` строили изменяемые объектные деревья. Структурные объекты ссылались на выбранные определения через `definer`.
3. `hyperatoms.py` связывал податомы серией индексов по массе, гиперномеру, текстовому идентификатору и имени.
4. `hyperatomic_map.py`, `hyperatom_tree.py` и `hyperatomic_graphs.py` собирали графы, а `graphviz_utilities.py` задавал оформление и размеры узлов.

Сильные идеи, которые стоит сохранить: отдельное объектное дерево, ссылки на определения вместо копирования целых поддеревьев, иерархический граф, фильтрация по группе элементов и сохранение DOT для последующей отрисовки.

Недостатки старой реализации, важные при переносе:

- старая грамматика принимает другой диалект и не должна быть вторым источником истины наряду с грамматикой версии 0.1.62;
- `hyperatoms.py` использует изменяемые глобальные/временные индексы, порядок обхода и присваивание в словари; при совпадающих ключах кандидаты могут молча перезаписываться;
- `by_element` сохраняет только первое определение символа, хотя один символ может иметь несколько шаблонов химического субэлемента;
- рекурсивная маркировка объектов использует изменяемые `tag` и не защищена общим множеством посещённых узлов; повторный вызов графинга может зависеть от предыдущего;
- `is_completed_hypernumber()` вручную перечисляет степени двойки только до 256, хотя иерархическая модель не ограничена этим списком;
- Graphviz-узлы нумеруются временными тегами вместо стабильных идентификаторов; часть фильтрации и размеров завязана на эвристики;
- `pygraphviz` обязателен даже для логики построения графа, а сохранение и отрисовка объединены в одном процессе;
- `bind_atoms` принудительно включает печать (`display = True`), поэтому библиотечный вызов имеет неожиданный побочный эффект.

## Новый конвейер

```text
.etoe source
  -> EToEParser / typed AST (single syntax authority)
  -> HyperatomTranslator
  -> HyperatomRegistry + semantic component references + diagnostics
  -> JSON for downstream simulation / analysis
  -> deterministic Graphviz DOT -> SVG / PNG / PDF
```

`etoe.hyperatom_translation` не дублирует грамматику и не меняет исходные `.etoe`. На каждое верхнеуровневое химическое утверждение создаётся `SemanticHyperatom` со стабильным ID, канонической записью, исходным файлом, индексом утверждения, символом, атомной массой, вторым числовым суффиксом `primary_mass` и семантическими компонентами. Поле `matter_level` различает атомную ступень E5 и молекулярную E6 по типу записи; `syntax_depth` — это глубина именно написанного выражения, а не претензия на физический атомный уровень.

Каждый компонент сохраняет исходную запись, разделитель, вложенную структуру, массу и происхождение массы. Для обычного числового компонента масса явная; для скобочной группы вроде `(5'5)` она может быть выведена как сумма известных масс компонентов. `mass_balance` проверяет соответствие суммы прямых компонентов объявленной массе, но не трактует это как доказательство физической правильности модели.

### Разрешение ссылок

- Числовой компонент индексируется по массе.
- Непосредственные субатомы, соединённые апострофом, канонически сортируются по убыванию известной массы. При одинаковой массе используется структурный текст, неизвестные массы идут после известных. Вложенные структуры нормализуются рекурсивно. Смешанные и иные разделители сохраняют исходный порядок.
- Исходное поле `canonical` остаётся точным представлением записи из `.etoe`. Для сравнения структур отдельно вычисляется `canonical_structure`, например `(8'4)`; символ элемента не включается в mass-qualified структурные токены. Поэтому определения разных символов с одинаковой конфигурацией получают общий ключ, но исходные записи не теряются.
- Если вложенная структура указана, она рассматривается как **частичный структурный шаблон**: явно записанные уровни сверяются, а отсутствующая глубина не считается утверждением об отсутствии внутренней структуры. Соседние субобъекты, разделённые апострофом, сопоставляются как неупорядоченное мультимножество (порядок не важен, кратность важна); иные/смешанные разделители остаются позиционными, пока их семантика не формализована.
- Символьный компонент разрешается в шаблоны соответствующего символа. Это может дать несколько кандидатов: они сохраняются все.
- Ссылки имеют статус `unique`, `ambiguous` или `unresolved`. Для встроенных обозначений, которые не имеют определения в каталоге, транслятор не выдумывает объект.
- Символы, неизвестные стандартному списку символов грамматики, но совпадающие с именем каталога элемента (в архиве это, например, `Nm` и `X`), распознаются как локальные символы элементного набора, а не автоматически трактуются как молекулы.

### Каноническая общая карта и runtime-патчинг

`build_canonical_hyperatom_map(registry)` строит индекс `by_structure` и список связей субатомов, используя нормализованное текстовое представление структуры. Атомный уровень вычисляется отдельно от ступени материи `E5`: для установленной структуры применяется правило `L_atomic = 1 + max(L_atomic(subatom))`. Масса сама по себе не определяет атомный уровень каждой возможной конфигурации.

Опция `build_canonical_hyperatom_map(registry, auto_patch_missing=True)` дополняет отсутствующие **конкретные субатомы с известной массой**, только если у ссылки нет кандидатов. Для найденного по вложенной структуре уровня используется структурный вывод. Для ссылки только на массу, где структура отсутствует, используется `floor(log2(mass)) + 1` как резервное приближение по первичной последовательности; источник вывода записывается в `atomic_level_source`. Вспомогательные символы имеют вид `X<n>` в смысле `X` плюс номер уровня (например, `X7`) и добавляются в `ElementCatalog` как runtime auxiliary records. Они не записываются в каталог файловой системы и маркируются метаданными `runtime=true`.

Автоматическое дополнение не устраняет неоднозначность: если у ссылки уже есть несколько подходящих кандидатов, все кандидаты сохраняются. Так как масса не задаёт уникальный уровень и структуру произвольного гиператома, резервный уровень для mass-only-ссылки является явно помеченным инженерным допущением, а не утверждением, гарантированным теорией.

Граф также не скрывает неоднозначность. Уникальная ссылка рисуется прямым ребром. Несколько кандидатов показываются через промежуточный ромбовидный узел со штриховыми рёбрами `candidate`; отсутствующая ссылка отображается отдельным нерешённым узлом. Поэтому граф не выдаёт предположение за установленную связь.

## Запуск

Из корня проекта после установки в editable-режиме:

```bash
python -m pip install -e .

# Перевести все .etoe в машинно-читаемый JSON
python -m etoe hyperatoms translate \
  --data-root data/atom/element \
  --output build/hyperatoms.semantic.json

# Построить каноническую карту и индекс структурных текстовых ключей
python -m etoe hyperatoms map \
  --data-root data/atom/element \
  --output build/hyperatoms.map.json

# Та же карта с runtime-заполнителями X<n> для ненайденных субатомов
python -m etoe hyperatoms map \
  --data-root data/atom/element \
  --auto-patch-missing \
  --output build/hyperatoms.patched-map.json

# Основная карта гиператомов в SVG
python -m etoe hyperatoms graph \
  --data-root data/atom/element \
  --output build/hyperatoms.svg

# Автоматически патченная карта; X<n> добавляются в память только на время процесса
python -m etoe hyperatoms graph \
  --data-root data/atom/element \
  --auto-patch-missing \
  --output build/hyperatoms.patched.svg

# Вариант с шаблонами элементов и химических субэлементов
python -m etoe hyperatoms graph \
  --data-root data/atom/element \
  --include-templates \
  --output build/hyperatoms-with-templates.svg

# DOT без установленного Graphviz; рендеринг SVG/PNG/PDF требует бинарник Graphviz
python -m etoe hyperatoms graph \
  --data-root data/atom/element \
  --output build/hyperatoms.dot

# Ограничить стартовый набор элементов; зависимые узлы включаются по композиционным ссылкам
python -m etoe hyperatoms graph \
  --data-root data/atom/element \
  --symbols Fe,Co,Ni,Cu \
  --output build/iron-group.svg
```

Graphviz engine задаётся через `--layout dot|neato|fdp|sfdp|circo|twopi`; формат определяется расширением выходного файла или `--format`. DOT генерируется стандартной библиотекой Python, без обязательного Python-пакета `graphviz` или `pygraphviz`.

## Контроль по архивному корпусу

В `etoe-0.1.62/data/atom/element` обнаружены **123 файла**, **457 синтаксических утверждений** и **457 семантических записей**. После учёта локальных символов `Nm` и `X` реестр содержит **293 гиператомные записи**, **163 шаблона элемента** и **1 запись голого символа элемента**. Все **287 записей с объявленной массой и непосредственными компонентами** в проверенном корпусе проходят проверку суммы масс. Для исходного корпуса транслятор сообщил **378 неоднозначных** и **10 неразрешённых** компонентных ссылок; это не означает, что исходные данные обязательно ошибочны — например, несколько шаблонов одного символа могут быть осмысленными альтернативами, а точное совпадение частичного структурного шаблона иногда отсутствует в наборе определений.

## Граница достоверности

Этот слой — формализация **явно представленной структуры данных** для дальнейшей симуляции, визуализации и проверки. Он не вводит неизвестные физические уравнения для взаимодействий, устойчивости или динамики гиператомов и не утверждает, что ÆToE подтверждена экспериментально. Для полноценной динамической модели понадобятся нормативные правила связывания неоднозначных субатомов, семантика всех разделителей/их параметров и определённые законы переходов между состояниями.
